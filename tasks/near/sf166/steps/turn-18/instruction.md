One more thing: ## Decision review: Opt-in SQLAlchemy 2.0 integration for Ariadne ### Product decisions in this change 1. **The SQLAlchemy integration is opt-in, scoped to `ariadne.contrib`, and marked experimental.** Users must explicitly install `ariadne[sqlalchemy]`; nothing changes for existing users. 2. **Two distinct execution paths cooperate rather than one unified approach.** Auto-resolved fields go through query lookahead (one optimized statement). Manually-resolved fields silently fall back to per-request that type batching. The path taken by any given field depends on whether it was registered with `SQLAlchemyQueryType`. 3. **`AsyncSession` is accepted as input but its concurrent-query limitation is documented rather than prevented.** Two sibling root fields in a single query (e.g. `{ users { ... } posts { ... } }`) race on the session's single underlying connection and produce a runtime error from SQLAlchemy — not from Ariadne. 4. **Session lifecycle is entirely the user's responsibility.** The integration reads a session from context but has no mechanism for opening or closing it. The documentation acknowledges that without a custom `Extension`, the session closes when the connection is reclaimed by GC. 5. **Relationship traversal depth has a global limit (default 3) that surfaces as a `GraphQLError` to the client when exceeded.** Per-type limits can only reduce, never increase, the inherited bound. 6. **Customizing context lookups (which key holds the session, which key holds the registry) requires subclassing**, not construction-time parameters. 7. **The that type fallback is async-only**, requiring `aiodataloader`. Sync stacks (`graphql_sync`, Django WSGI) cannot use the fallback path. 8. **The base `ObjectType.set_alias()` method now accepts callables** in addition to attribute name strings, changing the signature of a core public API. 9. **that type caches are scoped to one request** via a per-request `LoaderRegistry`. Sharing a registry across requests would leak data between users. 10. **Scalar fields are automatically loaded column-only, including FK columns the client did not explicitly request**, to ensure that type fallback can resolve relationships when needed. --- ### Assessment **1. Opt-in experimental positioning — agree.** Placing a new ORM integration in `ariadne.contrib` behind an optional extra is correct. Ariadne's settled design principle is no global state and explicit opt-in for integrations. Marking it experimental sets the right expectation that the API may change before stabilizing. **2. Two-path execution model — partially agree; the silent mode switch is a user experience risk.** | Option | What it gives users | What it costs | Effort to change later | |--------|---------------------|---------------|------------------------| | Current: auto-eager + that type fallback | Zero configuration for the common case; manual resolvers "just work" | Users must understand two paths and when each fires; performance characteristics differ silently | High — changes how all resolver authors think about the integration | | Single path: everything through DataLoaders | Uniform mental model; no "which path am I on?" question | Higher baseline overhead; loses the lookahead optimization for auto-resolved fields | Medium | | Single path: require explicit eager-load config everywhere | Predictable, no magic | High boilerplate; contradicts the "zero-boilerplate" positioning | Medium | The current design is pragmatic and the performance story is compelling. The risk is that a user writing a manual `@field` resolver doesn't realize they've switched execution paths — their query is now slower, and if `SQLAlchemyDataLoaderExtension` is not installed, it raises a `RuntimeError` at runtime rather than at schema-build time. Consider whether the fallback path should warn (in debug mode) or whether its absence should be detectable earlier. **3. AsyncSession concurrent-query limitation documented but not prevented — disagree; this is a footgun that should be gated.** `AsyncSession` is the obvious choice for an ASGI-native library. Users coming from the FastAPI/Starlette world will reach for it first. When two root fields are selected in one query — which is completely normal — they will see a cryptic SQLAlchemy `InvalidRequestError`, not an Ariadne error, and the connection between "I used `AsyncSession`" and "sibling fields race" is non-obvious. | Option | What it gives users | What it costs | Effort to change later | |--------|---------------------|---------------|------------------------| | Current: accept `AsyncSession`, document the limitation | Users can use `AsyncSession` for single-root-field queries | `InvalidRequestError` for any multi-root query; hard to diagnose | Low — just updating docs/behavior | | Detect `AsyncSession` at resolver call time, raise a descriptive Ariadne error | Clear error message pointing to the root cause | Still broken; just better message | Low | | Reject `AsyncSession` at construction time | Prevents the confusion entirely; directs users to the sync + thread-pool pattern | Removes a use case | Low — hard to walk back once shipped | | Enforce sequential execution when `AsyncSession` is detected | Preserves `AsyncSession` support without the race | Adds complexity; degrades performance for safe cases | High | For an experimental API, rejecting `AsyncSession` at construction time until the concurrency problem is solved is the least-bad option. If `AsyncSession` must be accepted, a detection-and-descriptive-error approach at the start of execution would at least tell users what went wrong. **4. Session lifecycle not managed by the integration — disagree; this undermines the "zero-boilerplate" claim.** The integration is positioned as "zero-boilerplate resolvers" in the PR description and README. But session lifecycle — opening, closing, scoping to a request, rolling back on error — is substantial boilerplate that the integration leaves entirely to users. The Quick Start example creates a session in `get_context` with no cleanup, which is incorrect in production. `SQLAlchemyDataLoaderExtension` manages one lifecycle concern (registry per request) but not the adjacent concern (session per request). Users will naturally ask "why does the extension handle the registry but not the session?" The inconsistency is likely to lead to production bugs in early adopters. A `SQLAlchemySessionExtension` — even a simple one that wraps a `sessionmaker` and closes the session in `request_finished` — would make the lifecycle story complete and the "zero-boilerplate" claim honest. Without it, the integration is zero-boilerplate only for the resolver layer, not the infrastructure layer. **5. Depth limit raises `GraphQLError` to the client — agree with reservations.** Raising an error is better than silently returning incomplete data. The error message names the type that set the tightest limit, which aids debugging. The reservation: a `GraphQLError` is indistinguishable to the client from a query validation error. For operators, a depth limit exceeded at query time is arguably a configuration issue (`max_depth` too low) or a schema design issue, not a client query error. Consider whether this should also log a warning server-side and whether the error should be a server error (500-class) rather than surfaced in the `errors` array. For now, the current behavior is acceptable in an experimental API. **6. Subclassing as the extension mechanism for context lookups — disagree; this pattern creates friction at scale.** When `registry_key` is customized on `SQLAlchemyDataLoaderExtension`, the docs correctly note that `get_loader_registry_from_context` must be overridden on "every `SQLAlchemyObjectType` subclass you use." For a schema with 10 types, this means creating a base subclass and using it everywhere — or accepting that one wrong instance silently reads the wrong key. | Option | What it gives users | What it costs | Effort to change later | |--------|---------------------|---------------|------------------------| | Current: subclassing to override context lookup | Full control; no new API surface | Verbose; single customization requires a base class for every type; easy to forget one instance | Low — backward compatible to add alternative | | Accept `session_getter` / `registry_getter` callables at construction time | One-line customization; no subclassing; consistent with Ariadne's `context_value` callable pattern | Slightly larger constructor API | Low | Ariadne already uses the callable-as-customization pattern (`context_value`, `error_formatter`). Accepting optional callables at construction time on `SQLAlchemyQueryType` and `SQLAlchemyObjectType` is more in line with the library's existing conventions. **7. that type fallback is async-only — agree, but the documentation creates a false expectation.** The aiodataloader dependency is a coherent choice given that Ariadne's that type support is already async-first. The limitation is correctly documented in the dataloaders guide. The issue is that the README now lists "Automated integration with SQLAlchemy 2.0 for zero-boilerplate resolvers and N+1 prevention" without qualification. A Django user (WSGI, sync) will install `ariadne[sqlalchemy]`, get the integration, and discover that type fallback silently doesn't work for them only when a manual resolver fires. The README entry should note the async requirement, or the WSGI/Django documentation should explicitly address this integration's limitations on that stack. **8. `ObjectType.set_alias()` accepting callables — disagree with this change being in this PR.** `ObjectType` is a core public API. Making `set_alias` accept a callable broadens the contract and signals a new use case. The motivation appears to be enabling `SQLAlchemyObjectType`'s `aliases` parameter to accept resolver functions — but the Greptile analysis notes that the callable branch in `SQLAlchemyObjectType._bind_auto_resolvers` is dead code given the current type annotation (`dict[str, str]`). The two-sided change (base API + unreachable branch) suggests this wasn't fully thought through. The base API change should wait until there is a clear, functional use case for callable aliases that users actually need. **9. Per-request that type cache scoping — agree.** This is the only correct behavior. that type caches that outlive a request would leak data between users. The `LoaderRegistry` tied to an `Extension` lifecycle is the right model. Well-stated in the docs. **10. Automatic FK column inclusion in `load_only` — agree.** This is a non-obvious but correct implementation detail. If FK columns weren't included in `load_only`, that type fallback would fail trying to extract the join value from an unloaded attribute. Handling this automatically means users who mix eager-load and manual resolver paths don't hit silent `AttributeError`s. It is worth surfacing in the documentation so users understand why FK columns appear in the SQL even when not explicitly requested. --- ### Open questions 1. **What is the expected user experience when `AsyncSession` is used with a multi-root-field query?** Is the decision that users should simply not use `AsyncSession` with this integration, or is there a plan to support it properly? 2. **Is session lifecycle management planned for a follow-up PR, or is it intentionally left to users?** The "zero-boilerplate" positioning in the README and PR description implies the former. 3. **Are there Django/WSGI users in the target audience for this integration?** If so, the async-only that type fallback needs to either be extended for sync stacks or the integration needs to be clearly positioned as ASGI-only. 4. **What triggered the `set_alias` callable change in the base `ObjectType`?** If the goal is to support callable aliases in `SQLAlchemyObjectType`, that can be done within the SQLAlchemy module without touching the base API. 5. **Is there a plan to stabilize the API before removing the "experimental" label?** If yes, which of the subclassing-based customization points are candidates for changing to callable configuration before stabilization? --- ### Recommendation **Discuss first** The core implementation (eager-load path, that type batching, selection-set lookahead) is technically sound and the test coverage is thorough. Three product decisions should be resolved before this ships: the `AsyncSession` footgun needs to be gated or prevented rather than documented; the session lifecycle gap undermines the "zero-boilerplate" claim and will cause production bugs in early adopters; and the `set_alias` callable change to the core `ObjectType` API should be deferred until there's a concrete, working use case. The subclassing-as-customization pattern is a design direction question that should be answered for experimental APIs before users build patterns around it.
