One more thing: @willmcgugan I ended up opting for another approach: instead of operating on the code split in lines (which is a state we get only in some cases, such as displaying the line numbers) I kept my previous approach, but improved its performance: :fast_forward: the code-position indexing update. The improvement comes from the function that returns a "code index" from a "code position" : e.g. for this code snippet the position _"line 3 / character 15"_ must be translated to index _"168"_: With the new implementation of this function, instead of iterating on every character of the code to be able to do this conversion I first store the length of each line of code in a list (which is rather cheap to do, as it's simple calls to `str.find()`), and then use that information to do the conversion. (we need to do this conversion to be able to pass indexes to the `Text.stylize()` method) By doing so, in order to stylise some parts of a 200 lines of code snippet (the content of _"rich/columns.py"_) I get a performance penalty that is rather low. Performance with `%timeit` on a laptop that is doing other things in parallel is not perfect measurement of course :shrug: , but in this test rendering it with several stylised ranges takes 22.3ms in average, versus 21.6ms without stylised ranges: ![Screenshot from 2022-06-16 16-20-46](
