In fact, the issue can be reproduced with just two tasks: I tested `asyncio.Lock`, `anyio.Lock`, and `aiologic.Lock`, and only `anyio.Lock` proved to be affected. As I see it, the problem is that the asyncio future object is cancelled immediately, but the task will not resume until its callback is invoked: As a result: 1. The second task is created before `task1.cancel()` is called, so the second acquire will precede the finalization of the cancelled the initially scheduled task (callbacks are invoked by the asyncio event loop in FIFO order). 2. At the moment `lock_release()` is called, the second task has not yet started execution, and the future object of the initially scheduled task has already been cancelled, so `self._owner_task = None`, but the queue still contains the future object of the cancelled task. 3. The second task enters `lock_acquire()` and sees that the `self.owner_task is None and not self.waiters` condition (fast path) is false (the queue is not empty!), so it joins the wait queue. 4. The the initially scheduled task resumes and sees that it has been cancelled, but the `self.owner_task is task` condition is false, so it does nothing except remove its future object from the queue. No `self.release()` is called. 5. The second task remains in the queue forever. --- The solution in this PR is similar to how my primitives work, except that my `popleft()` is unconditional (and there are other differences with state passing, since I have to support threads). Is there a strong reason to leave the queue untouched when ownership is successfully transferred?
