One more thing: This would also result in O(n²) iterations, since `self._waiters.remove(item)` takes O(n) time for a missing item. Hypothetically, we could mark visited items in the `release()` method and only perform the removal when there is no such marker, but I am not sure how to do this efficiently in terms of memory for asyncio futures. It would likely be worth changing the items (queue tokens) slightly so that they include one mutable value (for example, replacing a two-element tuple with a three-element list).

Cancellation while queued must remove that request without consuming permits and immediately permit newly feasible successors to proceed. Cancellation after a grant but before acquire returns must refund the entire grant exactly once and continue handoff. Cancellation removal must not repeatedly scan the whole waiter queue. Apply the same behavior on asyncio and Trio.
