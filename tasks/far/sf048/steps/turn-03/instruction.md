There's something to adjust in /work/w00: PERF: read_csv emits pyarrow-backed string arrays directly from the C parser ## Summary For string columns under the default ``future.infer_string`` or ``dtype_backend="pyarrow"``, the C parser previously built an ``ndarray[object]`` of Python strs and downstream ``ArrowStringArray._from_sequence`` ran a per-chunk ``isna`` scan plus a second pass to construct the pyarrow buffers. This PR adds a new ``_string_pyarrow_utf8`` cdef in ``parsers.pyx`` that fills pyarrow's offsets / data / validity buffers directly from the tokenizer and returns a pyarrow-backed ExtensionArray, skipping both the intermediate object array and the downstream scan. - Targets ``pa.large_string()`` wrapped in ``ArrowStringArray`` for the default (``StringDtype(na_value=np.nan)``) path. - Targets ``pa.string()`` wrapped in ``ArrowExtensionArray`` for ``dtype_backend="pyarrow"``. - Gated on ``encoding_errors="strict"`` (other modes keep the object path for codec fidelity). - ``parse_dates`` columns are left as object ndarrays so ``to_datetime`` can take its fast tslibs path. - Pure-ASCII columns — detected with a block-wise high-bit OR-scan of the data buffer (auto-vectorizes) — skip ``validate(full=True)``, which was ~half the remaining conversion cost. Multibyte columns validate as before, and invalid UTF-8 still falls back to the object path and raises ``UnicodeDecodeError``. - The validity bitmap starts all-valid and clears bits on NA rows, so the common no-NA case does no per-token bitmap work. ## Benchmarks Measured at the current head (includes the ASCII validation skip; that commit alone was worth ~10-12% on ASCII workloads in an isolated A/B/A, e.g. 213 ms → 190 ms on 1M x 10 x 8-char). main = the merge-base, both sides built and measured back-to-back on the same machine; 8-char ASCII strings; GC-controlled, best of 7 x 2 batches, ``pd.read_csv("file.csv")`` default: | Workload | main | this PR | Speedup | |--------------------------------------|---------:|---------:|--------:| | 10 string cols, 1000-string pool | 592 ms | 193 ms | **3.1x** | | 5 string cols, all unique | 784 ms | 94 ms | **8.3x** | | 50k rows x 500 string cols | 2782 ms | 634 ms | **4.4x** | | 1 string col x 1M rows | 63 ms | 30 ms | **2.1x** | Peak RSS (single read in a fresh process, ``ru_maxrss`` minus pre-read RSS): | Workload | main | this PR | Reduction | |--------------------------------------|---------:|---------:|----------:| | 1M x 10 dedup | 354 MB | 172 MB | **-51%** | | 1M x 5 all-unique | 483 MB | 97 MB | **-80%** | | 50k x 500 | 1358 MB | 437 MB | **-68%** | | 1M x 1 | 66 MB | 42 MB | **-36%** | The savings scale with non-repeating strings because the old path allocated one ``PyUnicode`` per unique value; the new path stores bytes directly in pyarrow's data buffer with no Python-object tax. Chunks exceeding 2 GiB raise ``OverflowError`` — unreachable in practice with default chunk sizes, but worth flagging. - ``pa.large_string()`` (int64 offsets) for the default path to match ``StringDtype``'s pyarrow storage exactly (avoids a downstream cast). - Direct ``TextReader`` callers now get ``ArrowStringArray`` under ``future.infer_string``.
